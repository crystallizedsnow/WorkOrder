# 工单系统飞书 Channel 接入技术方案

## 一、背景

### 1.1 建设背景

当前工单系统已经具备基于 ReAct 模式的 AiAssistant、Go CLI、CLI Service 和工单后端调用链。用户可以通过现有 Web HTTP/SSE 接口向 Agent 发起请求，由 Agent 查询运行时 dataCode 和 Schema、构建 CLI 参数，并完成工单查询或经过 dry-run 确认的写操作。

现有系统尚未建立统一的消息 Channel 层，Agent 入口与 Web Controller 直接耦合，也没有飞书事件接收、平台身份映射、平台会话隔离和异步回复能力。因此，当前不能直接在飞书中以对话方式使用 Agent。

本期选择飞书作为首个外部 Channel。由于部署环境没有公网地址，采用飞书服务端 SDK 提供的 WebSocket 长连接接收事件，不采用公网 Webhook。

### 1.2 建设目标

本期目标如下：

1. 建立与平台无关的 Channel 接入层，使 Web 与飞书复用同一套 Agent 主循环和工单能力。
2. 通过飞书长连接接收机器人单聊消息，并将 Agent 结果回复到原单聊会话。
3. 建立飞书身份与工单用户的安全绑定关系，保证每次工单操作均以真实用户身份执行。
4. 消除现有登录方案中不适合多用户 Channel 场景的密码、Token、日志及并发隔离风险。
5. 保持现有 CLI Service Schema 契约、后端业务校验和 Agent 写操作 dry-run 确认语义不变。
6. 建立消息幂等、会话串行、失败恢复、审计追踪和运行状态监控能力。

### 1.3 非目标

本期不包含以下内容：

- 企业微信、钉钉、Slack、Teams 等其他 Channel 的具体实现。
- 飞书群聊、群聊 @机器人及群线程场景。
- 语音、视频及复杂文件内容理解。
- 后端项目内新增 Web 页面；本期只改造后端接口，不建设绑定页面。
- 允许用户直接在飞书对话中提交工单账号密码。
- 在 Channel 或 skill 中重复维护具体工单接口字段和业务规则。
- 以飞书机器人应用身份替代工单系统用户身份执行工单操作。

### 1.4 设计原则

- **后端是业务与身份事实来源**：用户状态、角色、权限、绑定关系和访问令牌由后端统一管理。
- **Channel 只负责消息适配**：飞书事件解析和发送能力不得侵入 Agent 业务逻辑。
- **身份与会话分离**：平台会话用于上下文隔离，工单用户身份用于鉴权，两者不得混用。
- **最小权限**：首期只接收用户发给机器人的单聊消息，不申请任何群聊消息权限。
- **异步处理**：飞书事件处理线程只做校验、去重和投递，不同步等待 Agent 执行结束。
- **写操作可确认、可审计、不可重放**：所有写操作继续执行 dry-run，确认状态由服务端持久化。
- **通用修复**：登录与 Token 改造同时覆盖 Web、CLI 和 Channel，不为飞书编写孤立的鉴权补丁。

## 二、现状调研与问题评估

### 2.1 当前业务调用链

当前 Web 对话调用链如下：

```text
Web 页面
  → AiAssistant /assistant/chat（memoryId、message、Authorization）
  → AgentLoop 设置 sessionId 和 Token 上下文
  → LLM ReAct 循环
  → ToolDispatcher
  → Go CLI 进程
  → CLI Service /api/query 或 /api/execute
  → CLI Service 调用后端 /api/auth/validate 校验 Token
  → CLI Service 通过 OpenFeign 调用后端业务接口
  → Agent 生成最终回答
  → SSE 返回 Web 页面
```

该链路中的 Agent、运行时 Schema 查询、CLI 参数构建和后端业务接口均可复用。飞书接入的核心改造点是 Agent 之前的消息入口，以及贯穿 Agent、Go CLI、CLI Service、后端的用户身份上下文。

### 2.2 当前登录与 Token 链路

现有登录流程如下：

```text
用户或 Agent 提供手机号、密码
  → Go CLI 或 AiAssistant 直接请求后端 /user/login
  → 后端按手机号查询 Staff
  → 直接比较提交密码与数据库密码
  → 后端使用固定密钥签发 JWT
  → Go CLI/AiAssistant 将 Token 保存到用户目录
  → 同时将手机号和密码保存到本地 account 文件
  → Token 过期后读取 account 文件自动重新登录
```

请求执行时：

```text
Go CLI 从配置、环境变量或本地文件读取 Token
  → Authorization 原样传给 CLI Service
  → CLI Service 调用后端 /api/auth/validate
  → 后端验证 JWT 并从 JWT Claims 还原用户
  → CLI Service 再将同一 Token 转发到后端业务接口
```

### 2.3 合理性评估

现有方案在单开发者、本地调试环境中链路简单，但不适合飞书多用户及生产环境，评估为必须先改造再开放 Channel 写操作。

| 问题 | 当前表现 | 风险 | 结论 |
|---|---|---|---|
| 密码存储 | 后端直接比较密码；Go CLI 与 AiAssistant 将密码写入本地文件 | 数据库或主机泄露后可直接获得用户密码 | 必须改造 |
| 密码传递 | Agent 工具可接收手机号和密码 | 密码可能进入飞书、LLM 上下文、工具参数和审计日志 | Channel 场景禁止 |
| 敏感日志 | 登录请求对象、Token、用户对象存在被完整记录的可能 | 密码、JWT 和个人信息泄露 | 必须改造 |
| JWT 密钥 | 签名密钥硬编码在源码中 | 源码泄露即意味着所有 Token 可被伪造，且无法安全轮换 | 必须改造 |
| Token 生命周期 | 后端 JWT 有效期与客户端本地过期时间不一致 | 客户端认为有效但后端已经拒绝，触发不可靠重登 | 必须统一 |
| 刷新与撤销 | 无 Refresh Token、会话版本或撤销能力 | 用户离职、改密、禁用后旧 Token 在过期前仍可能有效 | 必须改造 |
| 用户实时状态 | JWT 包含角色、部门、状态等快照 | 用户权限变化无法及时生效 | 高风险操作需实时校验 |
| 多用户隔离 | Agent 存在全局 Token 缓存和单一 Token 文件 | 并发请求可能串用身份 | Channel 上线阻塞项 |
| 鉴权重复 | 后端同时存在安全过滤器与 MVC 登录拦截器 | 认证逻辑重复、Header 约定不统一、维护复杂 | 应统一入口 |
| Token 展示 | CLI 登录和状态结果可能返回完整 Token | 终端记录、Agent 上下文和日志可能泄露凭证 | 必须脱敏 |

### 2.4 飞书接入约束

- 飞书长连接只要求 AiAssistant 所在环境能够主动访问飞书公网，不要求公网 IP 或回调域名。
- 飞书接收消息事件要求快速完成处理；耗时 Agent 调用必须进入异步执行队列。
- 飞书事件可能重复推送，消息处理必须以平台 messageId 做幂等，不能只依赖 eventId。
- 飞书机器人凭证只证明机器人应用身份，不能证明工单系统用户身份。
- 本期只处理单聊，会话按飞书租户、机器人账号和发送用户隔离。
- 本期只部署一个 AiAssistant 实例，不建设长连接主节点选举；消息幂等和会话串行仍按可持久化方式实现，为故障重启和后续扩容保留基础。

### 2.5 三类入口及鉴权影响结论

本次改造涉及三类入口。三者共享后端用户和权限体系，但登录或换票方式不同。

| 入口 | 当前方式 | 本期目标方式 | 对现有调用方的影响 |
|---|---|---|---|
| 工单 Web 业务请求 | Web 调用后端登录接口取得 JWT，后续请求携带 Authorization，后端逐请求验 Token | 保留“直接登录 + 请求携带 Token + 后端逐请求验 Token”的总体链路；统一为标准 Bearer Access Token，并增加刷新、注销和撤销 | 业务接口和逐请求鉴权语义不变；所有调用方必须同步切换 Header 格式和过期续期方式，不保留旧格式 |
| AiAssistant HTTP 接口 | 调用方将 Authorization 传给 `/assistant/chat`，Agent 将同一 Token 传递到 CLI 链路 | 保留调用方先登录、再携带用户 Access Token 调用 Agent 接口；AiAssistant 必须在进入 Agent 前校验 Token，并将认证结果写入当前请求的不可变安全上下文 | `/assistant/chat` 可保留现有路径与消息参数；需规范 Bearer Header、拒绝无效 Token，并消除全局缓存和跨请求 Token 回退 |
| 飞书 Channel | 当前不存在 | 飞书用户先完成一次性账号绑定；消息到达后 AiAssistant 使用服务身份向后端换取该用户的短期代理 Access Token，再进入同一 Agent/CLI 链路 | 不要求用户在飞书输入账号密码，不复用某个 Web/CLI 用户的本地 Token，也不改变后端最终按真实用户鉴权的原则 |

因此，本期不是用飞书鉴权替换已有 JWT 鉴权，也不是让 AiAssistant 绕过后端认证。改造后的共同边界为：进入工单业务接口的每个请求仍必须携带后端认可的用户 Access Token，后端仍对每次请求建立安全上下文并执行权限检查；差别仅在于 Web/Agent HTTP 调用方通过用户登录获得 Token，而飞书 Channel 通过已经确认的绑定关系和受限服务换票获得短期代理 Token。

## 三、目标架构与完整链路

### 3.1 总体架构

```text
飞书用户
  ↕ WebSocket 事件 / 飞书消息 API
Feishu Channel Adapter
  → 事件校验、消息解析、messageId 去重
  → 标准 InboundMessage
Channel Router
  → 身份绑定查询
  → 会话映射
  → 同会话串行队列
Agent Gateway
  → 构建 AgentRequest 和用户安全上下文
现有 AgentLoop
  → LLM / RAG / Skill / ToolDispatcher
Go CLI
  → 携带短期用户访问令牌
CLI Service
  → Token 校验、Schema、参数契约和审计
工单后端
  → 用户、权限、业务规则和数据
Agent 最终结果
  → 标准 OutboundMessage
Feishu Channel Adapter
  → 回复原消息或原会话
```

### 3.2 Channel 与 Agent 边界

Channel 层统一处理以下平台差异：

- 平台账号、租户、发送者、单聊会话和消息标识。
- 文本、富文本和基础附件元数据解析。
- 事件幂等、消息过滤、回复目标和发送限流。
- 平台错误码、重试、超时和长文本拆分。

Agent 只接收标准化请求，不感知飞书 SDK 的事件结构。标准请求至少包含：

- Channel 类型和机器人账号。
- 平台租户、会话、消息、发送者标识。
- 内部 sessionId 和 workorderUserId。
- 用户访问令牌或不可变安全上下文。
- 用户文本、消息类型和追踪标识。

### 3.3 会话边界

内部会话键由系统生成并持久化，不直接使用飞书字符串 ID 充当现有 Long 型 memoryId。

首期会话隔离规则：

| 场景 | 会话边界 | 原因 |
|---|---|---|
| 飞书单聊 | tenant + botAccount + user | 保持用户与机器人的连续对话，并隔离不同用户 |
| Web | 保留现有用户会话，同时补充用户归属校验 | 防止调用方伪造他人的 memoryId |

同一会话中的消息必须串行执行；不同会话允许并行。会话繁忙时向用户返回排队提示，避免同一用户连续消息引发上下文覆盖或写操作顺序错误。

### 3.4 查询业务链路

1. 用户单聊机器人提出工单查询。
2. 飞书通过 WebSocket 推送接收消息事件。
3. Channel 校验机器人账号和租户，过滤机器人消息及不支持的消息类型。
4. 使用 messageId 在共享存储中原子去重，记录事件已接收状态。
5. 根据飞书租户和用户稳定标识查询工单账号绑定关系。
6. 未绑定时只返回绑定引导，不向 Agent 暴露业务工具。
7. 已绑定时生成或加载内部会话，取得短期用户访问令牌。
8. 消息进入该会话的串行队列，Channel 处理线程立即结束。
9. Agent 按通用流程发现 dataCode、查询运行时 Schema、构建参数并调用 Go CLI。
10. CLI Service 验证用户身份并调用后端业务接口；后端按当前用户、角色和数据范围返回结果。
11. Agent 生成适合聊天展示的结果，Channel 回复原飞书会话。
12. 全链路记录 messageId、sessionId、userId、traceId 和 CLI traceId，但不记录敏感凭证。

### 3.5 写操作链路

1. 查询身份和参数构建过程与读操作一致。
2. Agent 按现有通用流程执行 dry-run，不发生业务写入。
3. 系统将 dry-run 结果和命令摘要保存为待确认记录，而不是仅依赖 LLM 历史。
4. 飞书向原请求人发送交互卡片，卡片提供确认执行和取消操作。
5. 确认动作校验原请求人、原会话、待确认记录、摘要、有效期和使用状态。
6. 校验通过后原子地将确认记录标记为执行中，再调用真实写命令。
7. 后端继续执行最终用户权限和业务字段校验。
8. 成功、失败或结果未知均写入审计记录并回复用户。
9. 重复点击、重复事件或超时确认不得再次执行同一写操作。

### 3.6 三类鉴权端到端链路

#### 3.6.1 现有 Web 直接访问后端

```text
用户在现有 Web 客户端输入工单账号凭证
  → Web 调用后端登录接口
  → 后端校验密码并返回短期 Access Token 和续期凭证
  → Web 后续请求携带 Bearer Access Token
  → 后端认证过滤链逐请求验签、检查会话/用户状态并建立用户上下文
  → 后端业务服务继续执行角色、数据范围和业务规则校验
```

该链路保留现有“Web 直接登录、请求中验 Token”的模式。后端业务 Controller 不因飞书接入改为匿名接口，也不接受飞书身份字段代替 Token。本次改造直接移除旧 Authorization 格式，后端只接受标准 Bearer Access Token；Web、AiAssistant、Go CLI 和 CLI Service 必须在同一版本窗口同步切换。

#### 3.6.2 现有 AiAssistant HTTP 接口

```text
调用方先通过后端登录取得用户 Access Token
  → 调用 /assistant/chat 并携带 Bearer Access Token
  → AiAssistant 在 Agent 执行前向后端校验 Token或使用统一认证能力完成校验
  → 校验结果绑定到本次 AgentRequest
  → Agent 调用 Go CLI 时只传递本次请求的 Token
  → CLI Service 与后端继续逐请求验 Token
```

本期必须取消以下行为：请求未提供 Token 时回退到服务器全局缓存、不同请求共享 Token、从服务器单一账号文件取得其他用户凭证。现有 `memoryId` 还必须校验归属于当前认证用户，不能仅凭客户端传值读取历史。这样改造会收紧旧接口行为：无 Token、无效 Token、Token 与会话不匹配的请求将返回未认证或禁止访问，而不再尝试隐式登录。

#### 3.6.3 新增飞书 Channel

```text
飞书单聊消息到达
  → AiAssistant 根据 tenantKey + unionId/openId 查询绑定
  → 未绑定：只返回绑定指引，不启动业务 Agent
  → 已绑定：AiAssistant 使用自身服务身份调用后端内部换票接口
  → 后端核验服务身份、绑定状态、工单用户状态和授权范围
  → 后端签发短期、限定受众和来源的用户代理 Access Token
  → Token 绑定到本次 AgentRequest，并沿 Agent → Go CLI → CLI Service → 后端传递
  → 后端以 Token 中的真实工单用户执行最终鉴权与业务校验
```

代理 Token 的权限不得超过绑定用户自身权限；AiAssistant 服务身份本身不具有工单业务操作权限。换票失败、绑定失效或用户被禁用时，本次消息不得进入可调用业务工具的 Agent 流程。

## 四、功能点

### 4.1 飞书应用与长连接管理

- 支持通过配置中心或安全环境变量配置 App ID、App Secret 和启用状态。
- 使用飞书官方 Java SDK 建立 WebSocket 长连接。
- 支持启动、停止、自动重连、退避、连接状态和健康检查。
- 首期支持单个飞书应用账号，内部数据模型保留多账号扩展字段。
- 凭证不得写入仓库、普通配置文件或日志。

### 4.2 飞书事件接收与解析

- 订阅接收消息事件。
- 支持机器人单聊文本。
- 过滤机器人自身及其他机器人消息，防止机器人循环对话。
- 对富文本提取可读文本；不支持的消息类型返回明确提示。
- 保留原始事件的必要诊断元数据，但对个人信息和消息正文设置保留期限。

### 4.3 消息幂等与异步执行

- 使用 tenant、botAccount 和 messageId 构成全局幂等键。
- 事件接收、入队和状态变更具备原子性。
- 消息状态至少包含已接收、处理中、成功、失败、结果未知。
- Agent 执行与飞书 SDK 回调线程隔离。
- 可重试错误执行有限次数退避；业务错误不自动重放。
- 写操作在结果未知时禁止自动重复执行，转入人工核查。

### 4.4 Channel 路由与统一消息模型

- 定义统一的入站消息、出站消息、Channel 生命周期和发送契约。
- 现有 Web Controller 与 Feishu Channel 都通过统一 Agent Gateway 调用 AgentLoop，但保留各自的入口鉴权方式。
- 平台特有的解析、发送、限流、重试逻辑保留在适配器中。
- Channel Manager 提供注册、启停、状态和账号查询能力。

### 4.5 身份绑定

- 使用飞书 tenantKey 与 unionId 作为优先绑定标识；openId 作为应用内定位标识保存，不单独作为跨应用用户主键。
- 一个有效飞书身份只能绑定一个有效工单用户；解绑和换绑必须经过工单系统认证。
- 绑定状态至少包含待绑定、有效、已解绑、已禁用。
- 工单用户被禁用、离职或无权限时，绑定关系不得绕过后端状态校验。
- 不允许在飞书聊天中输入工单密码完成绑定。

### 4.6 会话与记忆

- 建立平台会话到内部 sessionId 的持久化映射。
- 会话必须归属于绑定后的 workorderUserId。
- 短期聊天历史按用户和会话隔离；系统不提供跨会话长期记忆。
- 解绑、换绑后默认创建新会话，不继续使用原账号上下文。
- 支持会话过期、清理和用户主动清除上下文。

### 4.7 回复与交互

- 普通结果支持文本或富文本回复。
- 长消息按飞书限制安全分片，保持顺序并避免截断关键字段。
- 写操作确认优先使用交互卡片，卡片只展示操作摘要、影响范围、有效期和确认状态。
- 发送失败支持有限重试和告警；不得因发送失败自动重做已经完成的业务操作。

### 4.8 可观测性与审计

- 统一关联飞书 eventId、messageId、内部 sessionId、workorderUserId、Agent traceId 和 CLI traceId。
- 记录连接状态、事件数量、重复事件、排队时长、Agent 执行时长、发送失败和绑定失败指标。
- 登录密码、App Secret、Access Token、Refresh Token、完整 Authorization Header 永不进入日志。
- 写操作审计记录真实用户、来源 Channel、来源会话、dry-run 摘要、确认人和最终结果。

## 五、登录与鉴权改造方案

### 5.1 目标认证模型

采用“短期访问令牌 + 可撤销刷新会话 + 飞书身份绑定 + 后端代理换票”的统一模型。

身份分为三类：

| 身份 | 用途 | 凭证 |
|---|---|---|
| 工单用户 | 现有 Web 客户端、Go CLI 或其他客户端正常登录和业务授权 | 短期 Access Token + 受保护的 Refresh Token |
| 飞书机器人应用 | 接收和发送飞书消息 | 飞书 App 凭证，仅用于飞书 API |
| AiAssistant 服务 | 根据已绑定飞书身份申请用户代理令牌 | 服务身份凭证，限制调用内部换票接口 |

飞书机器人 Token 与工单 Access Token 完全分离，不允许互相替代。

### 5.2 密码登录改造

后端继续支持手机号或工号登录，但需要完成以下改造：

- 数据库只保存自适应哈希后的密码，不保存可逆密文或明文。
- 登录时使用安全密码校验器比较哈希。
- 对现有明文密码采用渐进迁移或一次性迁移方案；迁移前必须备份并准备回滚。
- 登录接口增加参数校验、失败次数限制、短期锁定和统一错误提示，避免枚举账号。
- 修改密码后递增用户认证版本，使已有刷新会话失效。
- 登录请求和用户实体日志执行字段级脱敏，实体默认字符串输出不得包含密码。

### 5.3 Token 改造

- JWT 签名密钥移出源码，进入密钥管理或部署密文配置，并支持密钥标识与轮换。
- Access Token 采用较短有效期，客户端只依据后端返回的过期时间，不自行假设有效期。
- Refresh Token 使用高强度随机值，服务端只保存哈希及设备、会话、过期、撤销状态。
- 刷新时执行轮换，旧 Refresh Token 立即失效；检测到旧 Token 重放时撤销对应会话族。
- Access Token 只保留稳定最小 Claims，例如用户 ID、会话 ID、认证版本、签发方、受众和过期时间。
- 用户角色、组织和状态等高变化信息由后端基于用户 ID 查询或通过短时缓存获得。
- 提供注销单会话、注销全部会话、禁用用户和改密后的统一撤销能力。
- Authorization Header 统一采用标准 Bearer 形式，直接移除旧格式，不设置双格式兼容期。

### 5.4 飞书账号绑定流程

本期不建设或依赖后端项目的 Web 页面。绑定采用“已登录工单客户端申请一次性绑定码 + 飞书单聊提交绑定码”的纯接口流程。现有 Web 客户端、Go CLI 或其他受信客户端均可在完成工单登录后调用后端接口申请绑定码；首期至少由 Go CLI 提供该能力，保证方案无需新增页面即可实施。

```text
用户通过现有 Web 客户端或 Go CLI 正常登录工单系统
  → 已登录客户端携带用户 Access Token 调用后端绑定码申请接口
  → 后端为当前工单用户生成短时有效、单次使用、仅用于飞书绑定的随机码
  → 用户在飞书中单聊机器人并提交绑定码
  → AiAssistant 将绑定码和当前飞书身份交给后端绑定确认接口
  → 后端使用 AiAssistant 服务身份鉴别调用方，校验绑定码、用户状态和现有绑定冲突
  → 后端原子写入飞书身份与工单用户映射，并立即消费绑定码
  → 机器人返回绑定成功的工单用户脱敏信息
```

绑定码必须具备足够随机性、短有效期、单次使用、用途限制、尝试次数限制和状态校验，后端只保存绑定码哈希。绑定码不包含用户 ID、Token 或可推导身份的信息。机器人绑定成功后只显示工号或姓名等脱敏摘要，供用户及时发现误绑。

解绑和换绑同样不依赖页面：用户通过已登录客户端携带 Access Token 调用后端解绑接口；换绑必须先完成解绑，再申请新的绑定码。为避免飞书账号失陷后解除保护，飞书聊天本身不提供直接解绑或换绑能力。用户在飞书中发送工单账号密码不是受支持的绑定方式。

### 5.5 飞书请求的用户代理鉴权

飞书消息到达后，AiAssistant 不读取本地账号文件，也不长期保存用户密码或 Refresh Token。推荐流程如下：

1. AiAssistant 使用受限服务身份调用后端内部 Channel 换票能力。
2. 后端校验服务身份、Channel、租户、飞书用户、绑定状态和工单用户状态。
3. 后端为该次会话签发短期用户代理 Access Token。
4. 代理 Token 标记真实用户、调用来源、Channel 会话和代理主体。
5. Agent 将该 Token 放入不可变的请求安全上下文，Go CLI 仅在当前进程调用中使用。
6. CLI Service 和后端沿用统一 Bearer Token 校验，并按真实用户权限处理业务。
7. 代理 Token 不写本地文件，不返回飞书，不进入 LLM 消息和工具结果。

内部换票接口必须只允许 AiAssistant 服务身份访问，并限制受众、来源、有效期和权限范围。其目的不是绕过用户鉴权，而是将已经由用户确认的飞书绑定安全地转换为短期、可审计的工单用户身份。

### 5.6 Agent 与 CLI 凭证隔离

- 移除 Agent 的全局 Token 缓存，改为每次 AgentRequest 自带不可变安全上下文。
- 不使用服务器用户目录下的单一 Token 文件为 Channel 用户提供凭证。
- Agent 启动 Go CLI 时，通过仅对当前子进程有效的安全通道传递短期 Token。
- CLI 输出不得返回完整 Token；登录和状态命令只显示脱敏状态与服务端过期时间。
- 移除 AiAssistant 通过工具读取本地明文账号并自动重登的 Channel 路径。
- 独立开发者使用 Go CLI 时仍可保留本地登录体验，但不得保存密码；Token 续期使用 Refresh Token 或重新交互登录。

### 5.7 后端统一认证入口

- 以 Spring Security 认证过滤链作为唯一 HTTP 身份建立入口。
- MVC 拦截器只承担与身份无关的追踪等职责，不再重复解析 JWT。
- 安全上下文中的主体只保存认证后的稳定用户标识和权限视图。
- `/api/auth/validate` 可在过渡期服务 CLI Service，长期可改为本地标准 JWT 验签加高风险实时状态检查，减少每个请求重复 RPC。
- 登录、刷新、注销、绑定、解绑、内部换票接口分别定义明确的访问策略和审计策略。

## 六、分组件实施方案

### 6.1 工单后端

后端作为身份第一事实来源，实施内容包括：

1. 改造密码哈希、登录限流、敏感日志和统一错误响应。
2. 建立 Access Token、Refresh Session、认证版本和撤销机制。
3. 将 JWT 密钥外置并支持轮换。
4. 建立外部 Channel 身份绑定模型和一次性绑定挑战。
5. 提供绑定查询、确认绑定、解绑和受限内部换票能力。
6. 对用户禁用、角色变化、改密和解绑执行及时失效处理。
7. 在审计中记录真实用户与 Channel 代理来源。
8. 统一 Spring Security 认证链，消除重复解析与敏感日志。

### 6.2 workorder-api 共享契约

- 增加认证、刷新会话、外部身份绑定和代理身份结果的共享 DTO/接口契约。
- 契约只描述身份语义，不泄露密码哈希、Refresh Token 等内部字段。
- 保持后端实现为身份和权限语义的第一事实来源。

### 6.3 CLI Service

- 统一支持标准 Bearer Access Token。
- 确保查询、Schema 和写操作的鉴权策略明确且一致。
- 继续将用户身份传递给后端，不使用固定系统账号代替用户。
- 对 Channel 代理 Token 记录来源审计字段，但业务授权仍以真实用户为准。
- 清理 Token 前缀片段、完整响应体等敏感日志。
- 保持运行时 list/schema 为 Agent 参数契约的第二事实来源。

### 6.4 Go CLI

- 移除本地明文密码文件和无参数自动密码重登。
- 支持服务端返回的真实过期时间和安全刷新流程。
- Token 状态输出脱敏，不在 JSON 结果中回显完整凭证。
- 支持当前子进程级临时凭证，避免 Channel 用户 Token 落盘。
- 保持现有 list、schema、query、execute 和 dry-run 行为不变。

### 6.5 AiAssistant

- 新增统一 Channel 模型、Channel Manager、Channel Router 和 Agent Gateway。
- 新增飞书长连接生命周期、事件解析、去重、异步队列、回复和健康状态。
- 新增身份绑定查询、内部换票、会话映射和同会话串行控制。
- 将 AgentLoop 的输入从零散 sessionId、query、Token 收敛为标准 AgentRequest。
- 移除全局 Token 缓存和 Channel 场景的本地账号文件依赖。
- 将写操作待确认状态持久化，并支持飞书确认卡片回调语义。
- 现有 `/assistant/chat` 入口通过同一 Agent Gateway 调用，保留“调用方携带用户 Token”的方式，避免形成两套 Agent 流程。

### 6.6 数据存储

建议使用现有关系数据库保存身份绑定、绑定挑战、Refresh Session 和写操作确认；使用 Redis 保存短期幂等键、会话锁、队列状态和短期缓存；MongoDB 继续保存聊天历史。

关键数据实体包括：

| 实体 | 核心用途 |
|---|---|
| 外部身份绑定 | 飞书 tenant/union/open 标识到工单用户的映射及状态 |
| 绑定挑战 | 一次性绑定凭证、过期时间和使用状态 |
| Refresh Session | 登录设备会话、Token 哈希、轮换与撤销状态 |
| Channel 会话映射 | 平台会话键到内部 sessionId 和用户归属 |
| 消息处理记录 | messageId 幂等、处理状态、重试和结果摘要 |
| 写操作确认 | dry-run 摘要、请求人、确认人、有效期和执行状态 |

数据库敏感字段应加密或仅保存不可逆哈希，并配置最小访问权限和数据保留周期。

### 6.7 飞书开放平台配置

1. 创建企业自建应用并开启机器人能力。
2. 选择使用长连接接收事件。
3. 订阅接收消息事件。
4. 申请读取用户发给机器人的单聊消息权限。
5. 申请以应用身份发送消息权限。
6. 为写操作确认卡片申请和配置所需的卡片交互能力。
7. 配置应用可用范围，首期只开放测试用户。
8. 发布应用版本。
9. 正式发布前复核权限，不申请任何群聊消息权限。

## 七、可靠性与安全设计

### 7.1 幂等

- 飞书消息以 messageId 为业务幂等标识。
- 写操作使用独立 operationId，消息幂等不能替代业务幂等。
- 确认记录从待确认到执行中的状态转换必须是原子操作。
- 后端写接口应在可行范围支持调用方幂等键，解决执行成功但响应丢失的问题。

### 7.2 超时与重试

- 飞书事件接收只负责入队，快速返回 SDK。
- Agent、CLI、CLI Service、后端和飞书发送分别设置超时。
- 查询类操作可按错误类型有限重试。
- 写操作只有在明确未到达业务端时才允许自动重试；结果未知时进入人工核查。
- 飞书发送失败只重试消息投递，不重复执行 Agent 工具和业务写入。

### 7.3 限流与防滥用

- 按飞书租户、用户和机器人账号分级限流。
- 绑定、登录和刷新接口使用更严格限流。
- 限制单条消息长度、附件大小、会话排队长度和单次 Agent 最大执行时间。

### 7.4 数据与隐私

- 仅保留完成路由、审计和故障排查所需的平台标识。
- 消息正文日志默认关闭或脱敏，原始事件设置短期保留。
- Agent 历史不得包含密码、Access Token、Refresh Token 和 App Secret。

### 7.5 配置与密钥

- 飞书 App Secret、JWT 密钥、服务身份凭证统一由安全配置提供。
- 开发、测试、生产使用不同飞书应用和不同密钥。
- 支持密钥轮换，轮换过程允许新旧密钥短时并存。
- 健康检查和诊断接口不得返回密钥或完整 Token。

## 九、验证与交付要求

### 9.1 验证层次

代码实现完成后，测试必须覆盖以下层次：

1. **单元测试**：消息解析、会话键、幂等、身份绑定、Token 生命周期、确认状态机和脱敏。
2. **组件测试**：模拟飞书事件进入 Channel，验证异步入队、Agent 调用和回复发送。
3. **服务集成测试**：AiAssistant、Go CLI、CLI Service 和后端真实联调。
4. **飞书沙箱验证**：测试企业、测试应用和测试用户的真实单聊长连接验证。
5. **安全测试**：越权、串号、Token 重放、绑定劫持、重复确认和敏感日志检查。
6. **故障测试**：长连接断开、Redis/Mongo 短时故障、LLM 超时、CLI 超时、后端超时和飞书发送失败。
7. **回归测试**：现有 Web 对话、查询、Schema、dry-run 和真实写操作能力保持可用。

### 9.2 必须覆盖的端到端场景

- 未绑定用户只能收到绑定引导。
- 用户在已登录客户端申请一次性绑定码并在飞书完成绑定后，可查询自己的工单。
- 不同用户并发查询不串 Token、不串会话、不串结果。
- 相同 messageId 重放不重复触发 Agent。
- 用户禁用、解绑或改密后，旧会话不能继续访问业务。
- 普通用户无法通过飞书执行管理员操作。
- 写操作先 dry-run，未确认不得执行。
- 只有原请求人可确认，确认过期或重复确认均不得执行。
- 写成功但飞书回复失败时不得再次写入。
- 服务重启后绑定、会话、幂等和待确认状态保持正确。
- 飞书长连接断开后能够恢复，并且恢复期间事件不会造成重复业务执行。
- 日志和测试输出中不存在密码、完整 Token 和 App Secret。

### 9.3 代码完成后的测试文档交付

本技术方案只定义测试范围，不提前固化尚未实现的接口和命令。代码完成后必须基于最终运行时契约新增独立测试交付物：

- 一份详细的测试实施 Markdown，说明环境准备、飞书应用配置、测试账号、启动顺序、用例步骤、预期结果、日志定位、数据清理和故障恢复。
- 可重复执行的自动化脚本，覆盖后端认证、身份绑定、CLI Service、Go CLI、Channel 组件和可自动化的端到端场景。
- 飞书真实客户端操作清单，覆盖无法完全脚本化的应用授权、机器人单聊、绑定码提交和交互卡片确认。
- 测试数据初始化与清理脚本，确保重复执行不会污染业务数据。
- 验证结果记录模板，包含版本、环境、执行人、traceId、结果和遗留问题。

测试脚本不得硬编码生产账号、密码、Token、飞书 App Secret 或固定业务数据；凭证通过测试环境安全配置注入，业务参数以最终后端和 CLI Service 运行时 Schema 为准。

### 9.4 验收标准

- 用户能够在飞书单聊场景中使用现有工单 Agent。
- 每次业务访问均可追溯到唯一真实工单用户和飞书来源。
- 多用户并发环境不存在全局 Token、身份串用和会话串话。
- 飞书重复事件和重复确认不会造成重复写入。
- 密码不再明文保存，敏感凭证不进入消息、LLM、工具结果和日志。
- 后端是用户状态和权限的最终判断者，Channel 不维护业务权限规则。
- Web 入口与飞书入口复用同一 Agent Gateway 和 AgentLoop。
- 自动化脚本、人工实施文档和验证记录均可独立复现验收结果。

## 十、风险与已确认约束

### 10.1 主要风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 现有密码可能为明文数据 | 密码迁移存在兼容和回滚风险 | 先盘点数据，采用渐进升级或离线迁移并保留回滚方案 |
| 绑定码被截获或猜测 | 飞书身份可能被错误绑定 | 高熵随机码、短有效期、单次使用、尝试次数限制、后端仅保存哈希 |
| 单实例故障 | 长连接与消息处理暂时不可用 | 自动重连、健康检查、持久化幂等状态和运维重启；后续扩容时再增加实例协调 |
| Agent 执行时间较长 | 用户误以为无响应并重复发送 | 入队后发送处理中提示，提供排队与超时状态 |
| 写操作响应丢失 | 结果未知时可能被错误重试 | 后端业务幂等键、状态查询和人工核查流程 |

### 10.2 已确认的本期产品约束

本期按照以下约束实施，不再作为待确认项：

1. 不建设或依赖后端项目的 Web 页面，允许改造后端认证、绑定和换票接口。
2. 本期只支持飞书机器人单聊，不处理群聊和线程。
3. 写操作使用飞书交互卡片完成确认或取消。
4. 本期只部署单个 AiAssistant 实例，不建设多实例长连接协调。
