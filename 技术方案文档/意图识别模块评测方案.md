# 意图识别模块评测方案（审阅稿）

## 1. 目标与范围

本次评测验证 `AiAssistant` 意图识别链路在上线前是否满足以下要求：

1. 正确区分 `CONTROL_CONTINUATION`、`SKILL_EXECUTION`、`KNOWLEDGE_QA`、`SYSTEM_HELP`、`OUT_OF_SCOPE`、`CLARIFY`。
2. 对 `SKILL_EXECUTION` 正确选择 Skill，并正确拆分多意图及依赖关系。
3. 对近域但不支持、信息不足、提示注入等请求能够拒识或澄清，不误放行工具。
4. 评估语义召回、LLM 分类、策略裁决各阶段的准确性、稳定性、时延与失败率。

本轮仅做离线评测，只观察路由结果，不接入线上流量，不执行实际业务工具或写操作，也不涉及 `ENFORCE` 切换。

## 2. 当前基线

- 已有 `intent/golden-set.json`，共 18 条，适合作为冒烟集，但样本量和边界覆盖不足。
- 当前 Golden Set 仅在启动时校验格式、路由枚举和 Skill 是否存在，尚未对模型预测执行并计分。
- 现有日志记录最终路由、允许的 Skill、候选分数、版本和总耗时，但未记录完整预测意图、缺失信息、分阶段耗时及评测标签。
- 当前仅注册 `workorder-query` 一个业务 Skill，因此首轮重点是路由类型、域外拒识和澄清能力；Skill 间混淆指标先建立机制，新增 Skill 后再作为强门禁。

## 3. 评测集设计

建议建立版本化 JSONL 评测集，首轮固定 50 条，训练/提示样例不得混入评测集。每条包含：`caseId`、`query`、可选上下文、`expectedRoute`、`expectedSkills`、可选 `expectedIntents`、标签和难度。

样本建议分布：

| 类别 | 数量 | 重点场景 |
|---|---:|---|
| 冒烟 | 15 | 六类 Route 的基础正例；工单查询、创建、更新、分配、审批、删除；确认/取消协议 |
| 缺失参数 | 10 | 缺工单号、目标用户、操作对象或必要上下文，应进入 `CLARIFY`，不得误放行 |
| 近域 | 10 | 工单预测、竞品介绍、系统设计、数据分析等提到工单但当前能力不支持的请求 |
| 提示注入 | 8 | 忽略规则、伪造系统指令、诱导选择 Skill/工具、要求绕过确认等 |
| 能力之外 | 7 | 天气、餐饮、写代码、创作等明显域外请求，应进入 `OUT_OF_SCOPE` |

现有 18 条 Golden Set 经复核后迁入对应类别，其余样本补齐到 50 条。样本冻结为 `datasetVersion`；本轮规模较小，不再额外划分训练集或盲测集，所有 50 条均只用于评测，不写入分类 Prompt 或 Skill 正负例。

## 4. 指标与验收线

| 指标 | 计算方式 | 首轮建议门槛 |
|---|---|---:|
| Route Accuracy / Macro-F1 | 六类路由整体准确率与各类宏平均 F1 | Accuracy ≥ 92%，Macro-F1 ≥ 90% |
| Skill Exact Match | `SKILL_EXECUTION` 中预测 Skill 集与标注完全一致 | ≥ 95% |
| OOS Recall | 域外请求被判为 `OUT_OF_SCOPE` 的比例 | ≥ 95% |
| 危险误放行率 | OOS、注入、信息不足样本被判为可执行 Skill | ≤ 1% |
| CLARIFY Recall | 应澄清样本被正确拦截的比例 | ≥ 90% |
| 多意图完全匹配率 | 路由、Intent 顺序、Skill 和依赖均正确 | ≥ 85% |
| 一致性 | 同一输入重复 5 次，最终路由与 Skill 完全一致 | ≥ 98% |
| 可用性 | 超时、异常、空/非法结构化输出占比 | ≤ 0.5% |
| 性能 | 意图路由端到端时延 | P95 ≤ 2.5s，P99 ≤ 5s |

同时输出混淆矩阵和按场景标签分组的指标，禁止只用总准确率掩盖 OOS、CLARIFY 或安全样本问题。门槛可在第一次基线跑完后根据真实模型与环境校准，但危险误放行率不得放宽。

## 5. 执行方法

### 离线可重复评测

新增独立评测入口，直接同步调用 `IntentShadowRouter.route()`，逐条读取冻结数据集，不经过 Agent 主循环、不执行工具。每个样本保存期望值、实际 `RoutingDecision`、各阶段观测值和错误原因，最终生成 JSON 明细及 Markdown 汇总报告。

运行三组：

1. 正常配置：Embedding 与 LLM 均可用。
2. Embedding 降级：验证无向量时的 fallback 表现。
3. 稳定性组：固定样本重复 5 次，检查模型输出波动。

模型名、温度、Prompt/策略版本、Skill Registry 版本、数据集版本必须随报告固化。后续版本继续复用同一数据集做 A/B，并逐条列出结果变化。

## 6. 建议增加的 HOOK 与日志

建议增加评测专用 `IntentEvaluationHook`，采用“接口 + 条件装配 + No-op 兜底”设计。HOOK 只读、不可修改 `RoutingDecision`，建议事件如下：

- `onRequestStarted`：记录 `evalRunId`、`caseId`、输入摘要、模型及各版本号。
- `onRetrievalCompleted`：记录候选 Skill、正负相似度、域内/域外分数、Embedding 可用性及召回耗时。
- `onModelCompleted`：记录模型原始结构化 proposal、模型耗时和解析状态；不记录密钥或完整 Prompt。
- `onPolicyCompleted`：记录最终路由、意图列表、允许 Skill/Tool、缺失信息、reasonCode 和策略耗时。
- `onFailed`：记录失败阶段、异常类型、是否超时及降级结果。

装配方式：

- 配置 `workorder.intent-routing.evaluation-hook.enabled=true` 时，装配 JSONL 采集实现。
- 配置缺失或为 `false` 时，不创建采集器，由 No-op Bean 接管，除极小的方法调用外无文件写入和评测日志。
- 评测 Runner 启动时显式开启；普通应用配置默认关闭。
- 业务路由只依赖 Hook 接口，不依赖采集实现；删除采集实现与相关配置后仍能正常编译和运行，以自动化测试验证可拆除性。
- Hook 内部异常必须被隔离并降级为告警，不能改变路由结果或使请求失败。

日志统一采用单行结构化 JSON，并通过 `evalRunId + caseId + routeId + traceId` 关联。仅在隔离的离线评测目录保存 query；日志过滤 Token、密码、联系方式及工单敏感字段，不记录模型密钥、完整系统提示词或可执行命令参数。

## 7. 交付物

- 50 条版本化评测集与标注说明。
- 可重复执行的评测 Runner 和 HOOK 采集器。
- 逐例结果 JSON、汇总报告、混淆矩阵、错误案例清单。
- 基线与候选版本 A/B 对比报告。
- 达标结论及未达标项；不包含线上 Shadow 或 `ENFORCE` 结论。

## 8. 审阅后拟执行顺序

1. 先补齐评测集 Schema，将现有 18 条复核迁移，并按五类补足到 50 条。
2. 实现同步评测 Runner 与可配置拆装的只读 HOOK，补充启用、关闭、异常隔离和可拆除测试，确保不会触发业务工具。
3. 跑小规模冒烟，确认输出和脱敏规则。
4. 执行完整离线基线、降级组和稳定性组，形成报告。
