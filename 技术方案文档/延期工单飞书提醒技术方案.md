# 延期工单飞书卡片提醒技术方案

## 1. 背景与目标

工单后端已经每 5 分钟扫描一次超过截止时间的工单，并通过 RabbitMQ 生成消息中心记录；AiAssistant 已具备飞书单聊接入、用户绑定、文本回复和交互卡片发送能力。

本次改造目标：

1. 工单首次变为“已超时（410）”时，向该工单的所有未完成处理人发送飞书卡片。
2. 仅向已建立有效飞书绑定、且工单账号仍有效的处理人推送；未绑定用户直接跳过，不报错、不发送绑定引导。
3. 一次扫描产生的提醒支持批量提交、逐接收人发送、失败重试和结果审计。
4. 保留现有消息中心入库能力，使站内消息与飞书提醒使用同一业务事件，但互不影响。

## 2. 现状调研

### 2.1 延期工单扫描

`WorkOrderServiceImpl.checkAndUpdateOverdueOrders()` 使用 `@Scheduled(fixedDelay = 5 * 60 * 1000)` 扫描：

- 当前时间已经超过 `deadlineTime`；
- 工单状态为处理中（400）或验收失败（670）。

扫描到工单后，代码将状态更新为已超时（410），然后调用 `workOrderMessageProducer.sendWorkOrderMessages(...)`，经 `workOrder.message.queue` 由消费者批量插入 `message` 表。

因此，现有链路的接收人设计意图确实是工单处理人，并且数据模型支持一个工单存在多个处理人（派单和申请协助都会新增 `handle_user_info.handle_type = 4` 的记录）。

### 2.2 当前接收人代码存在的问题

`WorkOrderHelper.getHandleUserIds(orderId)` 当前不能正确取得处理人：

1. 查询 `handle_user_info.handle_type` 时传入了工单状态 `DELAYED = 410`，正确值应为处理类型 `HANDLE = 4`。
2. 查询结果映射的是 `HandleUserInfo::getOrderId`，正确字段应为 `HandleUserInfo::getUserId`。
3. 没有过滤 `finished = false`，可能提醒已经完成个人处理任务的协助人。
4. 没有 `distinct`，历史或异常重复记录可能导致重复推送。

此外，定时任务在异步线程中执行，而 `WorkOrderMessageProducer` 使用 `StaffHolder.get().getId()` 取得发送人。定时任务没有登录用户上下文，存在空指针风险。系统事件必须显式使用“系统发送人”或允许 `senderId` 为空，不能依赖请求线程上下文。

### 2.3 当前消息中心链路

当前链路为：

```text
业务状态变化
  -> WorkOrderMessageProducer
  -> RabbitMQ: workOrder.message.queue
  -> WorkOrderMessageConsumer
  -> message 表
  -> 前端 POST /dashboard/pageMessages 分页拉取
```

`message` 表目前只有接收人、发送人、消息类型、文本、发送时间和逻辑删除字段，没有已读状态、业务对象标识、事件幂等键或投递状态。

### 2.4 飞书用户绑定方式

当前绑定采用一次性绑定码：

1. 已登录工单用户通过 CLI 申请一次性绑定码。
2. 用户在飞书单聊中把绑定码发给机器人。
3. AiAssistant 将 `code + tenantKey + unionId + openId` 交给工单后端确认。
4. 后端在 `external_identity_binding` 保存飞书身份与工单 `userId` 的映射。

有效绑定条件为：

- `platform = FEISHU`；
- `status = ACTIVE`；
- 工单用户存在且 `staff.status = 0`。

`unionId` 是租户内稳定身份，`openId` 是当前飞书应用直接发送消息时的寻址标识。主动单聊推送应使用绑定记录的 `openId`，并调用飞书消息 API 的 `receive_id_type=open_id`。

当前 AiAssistant 的 `FeishuChannelAdapter` 只支持按入站消息的 `chat_id` 回复，尚无按 `open_id` 主动发送、延期卡片模板、批量推送入口和投递结果记录。

## 3. 总体方案

推荐复用现有 RabbitMQ，把“消息生成”和“渠道投递”解耦：

```text
延期扫描（条件更新成功）
  -> 生成一条 WORK_ORDER_DELAYED 业务事件
  -> 消息中心消费者：写 message 表
  -> 飞书通知消费者/调度器：筛选 ACTIVE 绑定
  -> 批量调用 AiAssistant 内部推送接口
  -> AiAssistant 按 openId 拆分并发送飞书卡片
  -> 返回逐接收人结果，失败任务进入重试/死信
```

职责边界：

- 工单后端负责延期事实、处理人、用户有效性、绑定事实、事件幂等和投递任务状态。
- AiAssistant 负责飞书应用凭证、卡片模板、飞书 API 调用、平台限流和平台错误分类。
- 飞书推送失败不能回滚工单状态，也不能影响消息中心入库。

## 4. 后端改造

### 4.1 正确查询处理人

新增明确的方法，例如：

```java
List<Long> getUnfinishedHandlerUserIds(Long orderId)
```

查询条件：

- `order_id = orderId`
- `handle_type = HandleUserInfoHandleTypeEnum.HANDLE.getValue()`（值为 4）
- `finished = false`
- `deleted = 0`

结果取 `user_id` 并去重。结论是：延期提醒的业务接收人应为工单处理人，且一个工单可能有多个处理人，必须批量处理。

### 4.2 避免重复扫描和重复通知

状态更新必须使用条件更新：

```sql
UPDATE work_order
SET status = 410
WHERE id = ?
  AND status IN (400, 670)
  AND deadline_time < ?;
```

仅当受影响行数为 1 时发布延期事件。这样即使多实例同时扫描，也只有一个实例获得发送资格。

建议增加通知事件/投递表，至少包含：

- `event_id`：全局唯一；
- `event_type`：`WORK_ORDER_DELAYED`；
- `work_order_id`、`work_order_code`；
- `receiver_id`；
- `channel`：`MESSAGE_CENTER`、`FEISHU`；
- `status`：`PENDING/SENDING/SUCCEEDED/SKIPPED/RETRYING/FAILED`；
- `attempts`、`next_retry_time`、`last_error`；
- `created_at`、`sent_at`。

唯一键建议为 `(event_type, work_order_id, receiver_id, channel)`，防止 MQ 重投或服务重启造成重复提醒。若项目暂不引入 Outbox，最低限度也要在消费端建立该唯一幂等键。

### 4.3 系统发送人

调整 `sendWorkOrderMessages`，由调用方显式传入 `senderId`。延期扫描传固定的系统账号 ID；若数据库允许，也可以使用空值并在展示层显示“系统”。不再从 `StaffHolder` 隐式取值。

本次确定使用可配置的系统账号填充 `sender_id`，并保证该账号不能登录、不能执行人工业务操作。

### 4.4 批量筛选有效绑定

在后端新增内部批量查询能力，避免逐用户查询：

```text
POST /api/channel/identity/internal/batch-resolve
X-Workorder-Service-Key: <service-key>

{
  "platform": "FEISHU",
  "userIds": [12, 18, 25]
}
```

一次 SQL 联查 `external_identity_binding` 和 `staff`，仅返回：

- 绑定状态为 `ACTIVE`；
- 用户状态为有效；
- `open_id` 非空。

响应示例：

```json
{
  "bindings": [
    {"userId": 12, "tenantKey": "t1", "openId": "ou_xxx"},
    {"userId": 18, "tenantKey": "t1", "openId": "ou_yyy"}
  ]
}
```

未绑定、已解绑、已禁用或缺少 `openId` 的用户不出现在结果中，投递任务记为 `SKIPPED_UNBOUND`，不调用飞书接口。

## 5. AiAssistant 改造

### 5.1 内部批量推送接口

新增只允许工单后端调用的内部接口：

```text
POST /internal/channels/feishu/notifications/work-order-delayed:batch-send
X-Workorder-Service-Key: <service-key>
Idempotency-Key: <batch-id>
```

请求体：

```json
{
  "notifications": [
    {
      "eventId": "...",
      "userId": 12,
      "tenantKey": "t1",
      "openId": "ou_xxx",
      "workOrderId": 1001,
      "workOrderCode": "WO...",
      "title": "...",
      "deadlineTime": "2026-08-23T10:00:00+08:00"
    }
  ]
}
```

响应返回每一项的状态，而不是只返回批次总成功：

```json
{
  "results": [
    {"eventId": "...", "status": "SUCCEEDED", "messageId": "om_xxx"},
    {"eventId": "...", "status": "RETRYABLE_FAILED", "errorCode": "RATE_LIMIT"}
  ]
}
```

接口应限制最大批量（建议 100），校验服务密钥、请求大小和字段长度，不接受任意卡片 JSON，避免内部调用者注入危险链接或伪造卡片。

### 5.2 按用户主动发送

为 `FeishuChannelAdapter` 增加独立方法：

```java
sendCardToOpenId(String openId, Map<String, Object> card)
```

该方法使用 `receive_id_type=open_id`。现有按 `chat_id` 回复的方法保持不变，不能混用两种地址类型。

飞书发送接口本质上仍是一位接收人一次请求。“批量推送”在系统内体现为一次提交多条通知，由 AiAssistant 使用有界线程池拆分发送；并发数、每秒请求数和队列长度均配置化。不可使用无界并行流。

### 5.3 延期卡片

本次卡片只提供信息展示，不提供“查看工单”跳转按钮，也不提供“完成工单”这类直接写操作：

- 标题：`⏰ 工单已延期`；
- 工单编号；
- 工单标题；
- 原截止时间；
- 当前状态：已超时；
- 提示：请尽快处理；
卡片内容必须由结构化字段渲染并做长度限制。后续如需增加操作按钮，应单独评审跳转鉴权或写操作确认链路。

### 5.4 重试和错误分类

- 网络超时、飞书限流、5xx：指数退避重试，建议最多 3 次。
- openId 无效、应用无权限、用户不可达：不可重试，记录失败并告警。
- 部分成功：只重试失败项，成功项不得再次发送。
- 达到重试上限：进入死信或 `FAILED` 状态，支持后台人工重投。

AiAssistant 需要记录 `eventId`、飞书响应 `messageId`、耗时和错误码，但不得记录 App Secret、服务密钥或完整个人身份信息。

## 6. 推荐时序

```text
Scheduler
  -> 条件更新工单 400/670 -> 410
  -> 查询未完成处理人 userIds（批量、去重）
  -> 写延期事件/Outbox
  -> RabbitMQ

消息中心消费者
  -> 按 eventId + receiverId 幂等写 message

飞书投递消费者
  -> 批量查询 ACTIVE 绑定和有效用户
  -> 未绑定：SKIPPED_UNBOUND
  -> 已绑定：批量调用 AiAssistant
  -> AiAssistant 按 openId 发送卡片
  -> 回写逐项发送结果
```

## 7. 事务与一致性

推荐使用 Transactional Outbox：工单状态更新和事件记录在同一数据库事务提交，再由后台发布器投递 RabbitMQ。这样可以避免“状态已改为 410，但 MQ 发布失败导致永远没有提醒”。

一致性语义采用“业务事件至少一次投递 + 消费端幂等”，不追求分布式强事务。飞书属于外部系统，不参与数据库事务。

如果首期工期有限，可暂时保留直接发 RabbitMQ，但必须做到：

1. 条件更新成功后才发送；
2. RabbitMQ publisher confirm 和失败告警；
3. 消费端唯一键幂等；
4. 提供按时间范围补偿未投递事件的任务。

## 8. 配置与安全

- 后端与 AiAssistant 的内部接口使用独立服务密钥，生产环境从密钥管理或环境变量读取。
- 内部接口最好同时限制网络来源；有条件时使用 mTLS。
- `openId` 属于用户标识，日志中只保留脱敏值。
- 卡片跳转链接不得携带用户 Access Token；用户打开页面后走现有登录态。
- 飞书应用已经开通机器人主动发送单聊消息所需权限；发布前仍需在真实企业租户完成已绑定用户的主动触达回归测试。

## 9. 测试方案

### 9.1 单元测试

- 仅查询 `handle_type = 4 && finished = false` 的处理人，结果按 `userId` 去重。
- 未绑定、解绑、禁用用户均被跳过。
- 一个工单多个处理人生成多条独立投递任务。
- 同一延期事件重复消费不会重复入库或重复推送。
- `chat_id` 回复和 `open_id` 主动发送使用正确的 `receive_id_type`。
- 卡片字段为空、过长和包含特殊字符时可安全渲染。

### 9.2 集成测试

- 工单从 400/670 首次转为 410，消息中心和飞书各收到一次提醒。
- 两个已绑定处理人均收到；一个绑定、一个未绑定时只发送一个。
- 多实例同时扫描只产生一组提醒。
- RabbitMQ 重投、AiAssistant 超时、飞书限流时只重试失败项。
- 用户解绑或禁用后不再推送。

## 10. 分阶段实施与工作量

### 阶段一：前置缺陷修复（约 1 人日）

- 修复处理人查询的枚举和值映射错误。
- 过滤未完成处理人并去重。
- 去除定时任务对 `StaffHolder` 的依赖。
- 增加条件更新和基础测试。

### 阶段二：可用版本（约 3～5 人日）

- 后端批量解析有效绑定。
- AiAssistant 新增受保护的批量推送接口、`open_id` 发送和延期卡片。
- 后端消费延期事件并批量调用 AiAssistant。
- 增加有限重试、逐项结果日志和集成测试。

### 阶段三：生产可靠性（约 3～5 人日）

- Outbox、投递状态表、唯一幂等键。
- 死信、补偿任务、监控指标和告警。
- 多实例、故障恢复和压测。

完整生产化预计 7～11 人日，不含联调环境准备。飞书主动单聊权限已经开通，本次也不包含前端工单详情跳转页开发。

## 11. 验收标准

1. 工单首次延期后 5 分钟扫描周期内产生提醒。
2. 所有未完成处理人中，仅有效绑定用户收到飞书卡片。
3. 多处理人、重复事件、多实例扫描均不产生重复提醒。
4. 未绑定用户不收到任何飞书消息，也不收到绑定引导。
5. 飞书失败不影响工单延期状态和消息中心记录。
6. 可按 `eventId/workOrderId/userId` 查询每个接收人的投递结果。

## 12. 已确认的业务约束

1. 提醒对象仅包含尚未完成处理任务的工单处理人。
2. 本次卡片不需要“查看工单”按钮。
3. 消息中心记录的 `sender_id` 填充固定系统账号。
4. 同一工单只在首次进入已超时（410）状态时提醒一次。
5. 飞书应用已经开通机器人主动发送单聊消息所需权限。
