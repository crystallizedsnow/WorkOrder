# 部署与启动方案

本文以 Windows PowerShell 的本地开发环境为例，同时列出生产部署的关键要求。核心业务可只启动 Backend 和 Frontend；CLI 与 AI Assistant 按需启用。

## 1. 服务与依赖

| 组件 | 默认端口 | 必需性 | 用途 |
| --- | ---: | --- | --- |
| MySQL 8.x | 3306 | 必需 | 业务数据 |
| RabbitMQ 3.x | 5672 / 15672 | 必需 | 工单消息与延期通知 |
| Elasticsearch 8.x | 9200 | 必需 | 工单搜索；AI RAG 也会使用 |
| Canal 1.1.x | 11111 | 搜索链路必需 | MySQL 增量同步至 Elasticsearch |
| Redis 7.x | 6379 | CLI/AI 必需 | 写操作预览、渠道会话与去重 |
| MongoDB 6.x | 27017 | AI 必需 | 助手会话记忆 |
| Backend | 8080 | 必需 | 核心业务 API |
| CLI Service | 5000 | CLI/AI 必需 | CLI 网关 |
| AI Assistant | 8081 | 可选 | AI 对话和飞书渠道 |
| Frontend | 5173 | 可选 | Web 管理端 |

开发工具版本：JDK 17、Maven 3.9+（Backend 和 CLI Service 可使用 Maven Wrapper）、Node.js 24+、pnpm、Go 1.25。AI RAG 还需 `BAAI/bge-small-zh-v1.5` ONNX 模型，目录内至少包含 `tokenizer.json` 和 `onnx/model.onnx`。

## 2. 配置策略

本地配置文件均已设置为不提交：

- `backend/workorder-server/src/main/resources/application.yaml`
- `cli-service/src/main/resources/application.yaml`
- `AiAssistant/src/main/resources/application.yaml`
- `AiAssistant/src/main/resources/application-local.yaml`

启动前至少检查：

1. Backend 的 MySQL、RabbitMQ、Elasticsearch 和 Canal 连接地址可达。
2. Backend 的 `workorder.auth.channel-service-key` 与 AI Assistant 的 `workorder.channel.service-key` 一致。
3. CLI Service 的 Backend 地址正确，Redis 可用。
4. AI Assistant 的 Backend、CLI Service、MongoDB、Redis、Elasticsearch 和 CLI 可执行文件路径正确。
5. LLM API Key、飞书 App ID/App Secret 等凭据使用环境变量注入，不在 YAML 中写入真实值。

PowerShell 环境变量示例：

```powershell
$env:ZHIPU_API_KEY = "replace-me"
$env:FEISHU_ENABLED = "false"
$env:FEISHU_APP_ID = "replace-me"
$env:FEISHU_APP_SECRET = "replace-me"
```

> 已被 Git 跟踪的配置文件不会因新增 `.gitignore` 规则自动停止跟踪。需由仓库管理者确认团队配置策略后，将其从 Git 索引移除并提供无密钥的示例文件。曾出现在工作区或历史中的真实密钥应立即轮换。

## 3. 初始化数据库

连接 MySQL 后先执行基础脚本，再根据现有库版本顺序执行迁移：

```sql
source backend/workorder-server/src/main/resources/workorder.sql;
source backend/workorder-server/src/main/resources/organization.sql;
source backend/workorder-server/src/main/resources/auth_stage_one_migration.sql;
source backend/workorder-server/src/main/resources/auth_stage_two_migration.sql;
source backend/workorder-server/src/main/resources/workorder_migration.sql;
source backend/workorder-server/src/main/resources/message_work_order_link_migration.sql;
source backend/workorder-server/src/main/resources/work_order_delayed_notification_migration.sql;
```

`workorder.sql` 会创建并切换到 `wos` 数据库。对已有数据库执行前，先备份数据并阅读迁移脚本，不要无条件重复执行。

## 4. 构建

在仓库根目录依次执行：

```powershell
# 共享 API 和核心后端
Set-Location backend
.\mvnw.cmd clean install
Set-Location ..

# CLI Service（依赖本地 Maven 仓库中的 workorder-api）
Set-Location cli-service
.\mvnw.cmd clean package
Set-Location ..

# Go CLI
Set-Location workorder-cli
go build -o workorder-cli.exe .
Set-Location ..

# AI Assistant（可选）
Set-Location AiAssistant
mvn clean package
Set-Location ..

# Web 前端（可选）
Set-Location frontend
pnpm install --frozen-lockfile
pnpm build
Set-Location ..
```

## 5. 启动顺序

```text
MySQL → RabbitMQ → Elasticsearch → Canal → Redis/MongoDB
      → Backend → CLI Service → AI Assistant → Frontend
```

每个服务使用独立 PowerShell 窗口：

```powershell
# Backend
Set-Location backend
.\mvnw.cmd -pl workorder-server spring-boot:run

# CLI Service
Set-Location cli-service
.\mvnw.cmd spring-boot:run

# AI Assistant（可选）
Set-Location AiAssistant
mvn spring-boot:run

# Frontend（可选）
Set-Location frontend
pnpm dev
```

CLI 无需常驻进程。默认连接 Backend `http://localhost:8080` 和 CLI Service `http://localhost:5000`，可通过环境变量覆盖：

```powershell
$env:WORKORDER_BACKEND_URL = "http://localhost:8080"
$env:WORKORDER_CLI_SERVICE_URL = "http://localhost:5000"
.\workorder-cli\workorder-cli.exe auth status
```

## 6. 启动验证

| 检查项 | 地址或命令 | 预期 |
| --- | --- | --- |
| Backend API 文档 | `http://localhost:8080/doc.html` | 可打开 Knife4j |
| CLI Service | `http://localhost:5000/api/dataCodes` | 返回 dataCode 列表 |
| AI 健康检查 | `http://localhost:8081/actuator/health` | 状态为 `UP` 或明确指出未启用的可选依赖 |
| AI 首页 | `http://localhost:8081/assistant/` | 页面可打开 |
| Frontend | `http://localhost:5173` | 页面可打开，API 代理无报错 |
| Go CLI | `.\workorder-cli\workorder-cli.exe list` | 返回可用能力列表 |

完成基础检查后，再使用测试账号走通“登录 → 创建工单 → 审批 → 派单 → 处理 → 确认”链路，并确认 MySQL 数据可通过 Canal 同步到 Elasticsearch。

## 7. 常见问题

- **CLI Service 找不到 `workorder-api`**：先在 `backend` 下执行 `.\mvnw.cmd clean install`。
- **MySQL 有数据但搜索不到**：检查 Elasticsearch、Canal 和 destination `example`，再检查索引同步日志。
- **AI Assistant 启动失败**：检查 MongoDB、Redis、Elasticsearch、CLI 路径、ONNX 模型和 LLM API Key；不使用 RAG 时可关闭 `llm.embedding.enabled`。
- **401 或 Token 过期**：重新登录或刷新 Token，并确认各服务的 JWT/渠道密钥配置一致。
- **Frontend 请求失败**：确认 8080 和 8081 端口可用；开发代理分别使用 `/api/backend` 和 `/api/assistant`。

## 8. 生产部署要点

- 使用不可变构建产物或容器镜像，按依赖顺序发布，并配置存活/就绪检查。
- 通过密钥管理服务注入数据库、JWT、LLM 和飞书凭据；禁止将真实密钥打包进 JAR 或前端产物。
- 为 MySQL、RabbitMQ、Redis、MongoDB 和 Elasticsearch 启用认证、TLS、备份和最小网络访问范围。
- 前端静态文件使用 Nginx/CDN，只向外暴露必要 API；Knife4j、Actuator 和 RAG 管理端点限制在管理网络。
- 将服务日志与数据目录挂载到持久化存储，监控错误率、队列积压、搜索同步延迟和 RAG 健康状态。
- 升级前备份数据库并验证迁移；知识库回滚参见 [RAG 运维说明](RAG运维说明.md)。
