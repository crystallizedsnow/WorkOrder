# 消息跳转工单详情技术方案

## 1. 背景与目标

消息中心已经具备点击消息并跳转 `/work-orders/:id` 的前端逻辑，但 `/dashboard/pageMessages` 没有返回 `workOrderId`，消息表也没有保存消息与工单的关联，因此实际点击无法进入详情页。

本次改造要求新产生的工单消息携带工单 ID，消息列表接口返回该 ID，用户点击消息后进入对应工单详情页。不兼容未携带工单 ID 的历史消息，不从消息正文解析工单编号，也不回填历史数据。

## 2. 改造范围

消息产生链路调整为：

`工单业务操作 -> RabbitMQ 消息（workOrderId） -> message 表（work_order_id） -> 消息列表接口（workOrderId） -> 工单详情路由`

涉及以下模块：

- 工单消息生产参数与 RabbitMQ DTO。
- 消息消费及 `message` 表持久化。
- 消息列表接口的返回对象。
- 消息中心点击行为及历史消息提示。
- 初始化建表脚本和存量环境增量迁移脚本。

前端创建工单时还需将雪花算法生成的 `flowId` 保持为字符串传输，避免 19 位 ID 被 JavaScript `number` 截断，确保能够从界面创建用于验证的新消息。

## 3. 数据设计

`message` 表新增 `work_order_id BIGINT` 并建立普通索引。增量迁移中字段允许为空，用于保留现有历史消息；新消息由应用链路保证写入工单 ID。初始化脚本中的历史示例数据保持空值。

本次不增加外键约束。工单采用逻辑删除，消息仍需保留；工单不存在时沿用详情接口现有的业务错误处理，详情访问权限不在本需求中调整。

## 4. 接口设计

`POST /dashboard/pageMessages` 的单条记录新增：

```json
{
  "id": 1001,
  "workOrderId": 6,
  "content": "您收到编号为 WO... 的工单，请尽快处理。",
  "type": 400,
  "typeDesc": "处理中",
  "sendTime": "2026-09-07 10:00:00"
}
```

`id` 和 `workOrderId` 直接由消息实体映射到返回对象，不增加额外查询。

## 5. 业务处理

所有工单消息发布入口必须传入工单 ID，包括创建、审批流转、派单、处理、验收和超时提醒。消费者将 ID 写入每一条接收人消息。

前端收到非空 `workOrderId` 后跳转 `/work-orders/{workOrderId}`。历史消息的 `workOrderId` 为空时不尝试解析正文，提示“该历史消息未关联工单”。如果工单已删除，由现有详情接口返回业务错误。

## 6. 发布步骤

1. 先执行 `message_work_order_link_migration.sql` 增加字段和索引。
2. 再发布后端，使新消息写入并返回 `workOrderId`。
3. 最后发布前端。

数据库变更必须先于后端发布，否则消费者插入新消息时会因字段不存在而失败。

## 7. 验收标准

- 创建及流转工单后，新消息记录包含正确的 `work_order_id`。
- 消息列表接口返回消息 `id` 和 `workOrderId`。
- 点击新消息进入对应工单详情页。
- 多接收人消息均关联同一个工单 ID。
- 超时提醒消息也能跳转对应工单。
- 点击未关联工单 ID 的历史消息仅显示提示，不发起详情查询。
